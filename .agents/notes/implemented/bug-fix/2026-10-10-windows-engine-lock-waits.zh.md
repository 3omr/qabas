# Agent Note: 可取消的 Windows 引擎锁等待

Status: implemented

[English](2026-10-10-windows-engine-lock-waits.md) | 中文

## 问题

已安装的 Windows 引擎在并发操作于 OCR 或索引期间持有锁时，以 `[Launcher Error] [Errno 36] Resource deadlock avoided` 退出。CRT 的 `LK_LOCK` 只在有限的时间内重试，不像 POSIX 的 `flock(LOCK_EX)` 那样无限等待。把 Windows 上每个加锁 OSError 都当作争用，还会掩盖描述符错误和其他系统故障。试卷提取在运行缓慢的外部工具时一直占用讲座注册表锁。

## 决定

引擎通过反复执行 `LK_NBLCK` 获取 Windows 上第 0 字节的范围锁，每次尝试之间调用 `cancellation.wait(.05)`。POSIX 保留整个文件的 `flock` 互斥，并使用非阻塞尝试来实现可取消的等待。两个加锁辅助函数都接受以秒为单位的可选超时。非阻塞未获取和等待超时都会抛出 `ModuleBusy`，保持与 `AlreadyLocked` 和 `BlockingIOError` 的兼容；与争用无关的加锁 OSError 会向上传播。

持有者 JSON 从第 0 字节保留的空格之后开始写入，因此 Windows 上的争用方无需触碰被锁定的范围就能读取诊断信息。活动、准备和索引的持有者记录 `module`、`operation` 和 `pid`；讲座持有者还保留 `lecture_key` 和 `title`。启动器输出 `Module <module> is busy: <operation>; wait for it to finish`。移除操作保持现有的 ModuleConfigError 接口，同时保留持有者信息。取消会先释放活动句柄再删除租约文件，不需要再次进行可取消的入口锁获取。

准备流程用单独的锁串行处理每份试卷，并在整个提取过程中保持模块活动租约。受注册表保护的准备和发布步骤包围着在注册表锁之外执行的提取。发布时会重新检查源文件哈希和该试卷的准备记录，重新加载整个状态以保留其他写入者的结果，并拒绝写入一个新被占用的学生文本目标。源文件被修改或删除时需要重试，而不会得到过时的 OCR 文本。

桌面端编辑已经通过 `runMcpTool` 把取消和截止时间传给共享的子进程提供者。其 Windows 普通进程所有者使用关闭即终止的 Job Object，并以进程树 taskkill 作为回退。这项改动没有增加独立的终止器。[可逆移除的决定](../feature/2026-10-03-reversible-removals-and-fixed-library.zh.md)仍然负责模块准入和移除语义；本记录负责等待行为和持有者诊断。

## 考虑过的替代方案

**使用阻塞式原生等待的 LockFileEx。** 轮询现有的 CRT 原语避免了单独的原生 ABI，并让现有的取消模块能直接中断等待和执行截止时间。

**保留 LK_LOCK 并转换其最终的 errno。** 更清楚的错误信息仍然会拒绝一个持有者确实需要超过十秒的操作。

**在 OCR 期间保持注册表加锁。** 这会在整个外部提取期间排斥无关的注册表操作。按试卷串行化加上对源文件和记录的重新验证，在缩短注册表占用时间的同时保证了发布的安全。

**增加桌面端进程终止器。** 共享的子进程所有者已经会终止 Windows 进程范围；再加一个终止器会重复生命周期的所有权。

## 后果

默认情况下，被争用的锁可以无限等待，每次尝试之间检查取消，调用方也可以设置截止时间。轮询会带来少量周期性唤醒。持有者标签只是诊断信息，不能证明 PID 仍然存活；操作系统锁仍是判断活动的依据。提取期间源文件的变化会表现为可重试的准备错误，其他试卷已完成的结果保留在重新加载的状态中。

基于进程的回归测试覆盖：单个持有 15 秒的持有者、超时和立即未获取时的标签、及时取消、系统错误的传播、提取期间从另一个进程获取注册表锁、移除排斥、源文件替换、新被占用的输出文件以及取消后的清理。一份由所有者维护的预期输出文件固定了启动器的忙碌提示文本。Windows CI 使用 Python 3.12，安装引擎依赖，并在 `TRANSCRIBER_AGY=off` 下运行加锁、准备和模块活动的测试；Ubuntu 不变。原生 Windows 等待和已安装桌面端的子进程树取消仍需在 Windows 上验证。
