# Agent Note: Windows 上 NotebookLM 登录控制台的恢复

Status: implemented

[English](2026-10-10-windows-notebooklm-login-console.md) | 中文

## 问题

一名学生安装的 Windows 应用在重新连接 NotebookLM 时显示 `nlm.exe` 应用程序错误 `0xC0000142`。UV 工具跳板会启动由 UV 管理的 Python，但出错的组件和 DLL 初始化失败的原因尚未查明。登录所有者丢弃了退出状态，重建 PATH 时没有明确加入 Windows 系统目录，并在启动后立即释放了 ConPTY 主端。

## 决定

共享的本地代理环境保留继承的 Windows 操作系统变量，补齐缺失的系统默认值，并把 System32 和 Wbem 加入 PATH，同时排除凭据和加载器注入变量。在 Windows 上，NotebookLM 会一直持有 PTY 主端直到子进程退出，并在关闭时读完输出。portable-pty 以 `PSEUDOCONSOLE_INHERIT_CURSOR` 打开 ConPTY，因此 conhost 会在宿主回答光标位置请求之前一直挂起子进程；输出读取线程每读到一个 `ESC[6n`，就向 PTY 输入写入一个光标报告（`ESC[1;1R`）作为回答。在 conhost 发出请求之前写入的报告会被当作键盘输入读取（它正是 F3 键序列）。异常退出会公开十六进制状态以及只包含变量名称和 System32 是否存在的环境摘要。

Windows 上的 PTY 启动失败、`0xC0000142`，以及五秒内无输出就退出的情况，会用同样经过清理的环境打开一个普通的可见控制台。该控制台以 CREATE_NEW_CONSOLE 复用原生的挂起启动 Job 所有者，因此 UV 和 Python 在执行之前就进入了被持有的进程树。取消以及状态验证成功时会终止并等待该进程树。认证流会通知控制台已打开，继续执行现有的登录状态检查，直到连接成功或被取消，并把诊断信息放进界面中默认收起的展开区域。界面文案只有阿拉伯语和英语。

嵌入式登录和控制台恢复均传入 `--storage protected`，为新配置选择操作系统密钥库存储，跳过 CLI 的 1/2 问题。已有配置保留 CLI 原有的存储行为，不强制迁移。Google 登录仍需交互完成。Windows 回复以回车结束，表示 ConPTY 的 Enter 键；Unix 回复仍使用换行。在真实 Windows PTY 中，仅发送换行会回显答案，但 Python `input()` 继续等待；回车才能完成输入。

## 考虑过的替代方案

**只加固环境。** 现有的清理在变量存在时已经保留系统变量名。加固 PATH 解决了一个具体的遗漏，但无法证明或解决所有 ConPTY 或图形界面启动故障。

**始终使用外部控制台。** 嵌入式对话在正常的安装和其他操作系统上仍然有用。只有在上述 Windows 故障时，恢复流程才会打开控制台。

**把登录进程退出视为已连接。** CLI 结束并不代表会话有效。即使外部控制台已经退出，现有的 `nlm login --check` 仍然是判断授权的依据。

**自动输入存储选项。** CLI 提供 `--storage protected`；传入受支持的参数，无需解析终端文本或控制模拟输入的时机。

## 后果

Windows 回归测试等待真实 cmd 提示，通过正式管理器提交回复，再验证子进程已读取答案并退出。测试在断言之前终止并等待其独立子进程，超时路径亦如此。已安装 CLI 的帮助确认受保护存储参数会跳过新配置问题。本地原生执行需要 Rust 和 Windows 构建工具链；该测试由桌面 Windows CI 执行。

诊断信息不会暴露任何环境变量的值。外部控制台的尝试会一直保持等待，直到状态检查连接成功或学生取消；没有任意设定的认证超时。五秒静默退出规则也可能在一次快速成功退出后打开控制台，所以状态检查仍然是依据。

单元测试覆盖环境清理、Windows 上的系统变量、有符号和无符号 DLL 状态的分类、诊断展开区域以及本地化的控制台状态。由所有者维护的界面快照覆盖阿拉伯语和英语。Windows CI 明确通过正式的 PTY 辅助程序运行 cmd 和已安装的 Python。它不会安装 notebooklm-mcp-cli，因为该任务不需要安装 UV 工具。仍然需要一个真实安装的 Windows 应用来验证由 UV 管理的 Python、Google 登录、控制台的可见性、取消，以及这名学生报告的故障。
